## [ ] MAJOR OPERATIONS UPDATE: Automated Daily Encrypted PostgreSQL Backup to a Private GitHub Repository

### Objective

Add an off-instance database backup without changing the running application,
tenant provisioning, deployment, PostgreSQL volume, or current Phase 30
release flow. Every 24 hours the production EC2 host must create one
transactionally consistent PostgreSQL dump containing the `public` schema and
every serial/quantity tenant schema, encrypt it locally, upload it to a
dedicated **private personal GitHub repository**, verify the remote copy, and
remove transient plaintext.

This is a temporary, explicitly approved alternative to S3/object storage. It
provides a maximum scheduled recovery-point objective (RPO) of approximately
24 hours, but GitHub is not a database-backup service and is not the final
long-term disaster-recovery destination.

### Non-Negotiable Safety Decisions

1. Use a separate private repository such as `financee-db-backups`; never put
   production backups in the application repository.
2. Upload encrypted bundles as **GitHub Release assets**, not Git commits and
   not Git LFS. Normal Git objects are blocked above 100 MiB and permanently
   bloat repository history; each release asset must remain below GitHub's
   current 2 GiB per-file limit.
3. Back up PostgreSQL only in this job. Do not silently change
   `deploy/backup_encrypted.sh`, whose rehearsed Phase 28 contract includes both
   database and media. The existing full database-plus-media recovery path
   remains available and independent.
4. Never upload a plaintext dump, `.env`, database password, encryption
   passphrase, GitHub token, customer-readable manifest, application logs, or
   SSH key.
5. Store the encryption passphrase and GitHub credential in separate
   root-readable files on EC2 (`0600`), outside both repositories. The
   passphrase must also have a second offline copy controlled by the owner. A
   backup without its passphrase is unrecoverable.
6. Use a fine-grained GitHub credential restricted to only the private backup
   repository and only the permissions needed to create/list/delete releases
   and assets. Set an expiry date and document token rotation. Do not reuse the
   EC2 deployment SSH key or a broad classic personal access token.
7. Upload success alone is not success. The job must download the new remote
   asset to a new temporary path, compare its SHA-256 checksum, decrypt/list
   the bundle, and confirm that `pg_restore --list` can read the contained
   custom-format dump before reporting success.
8. Use UTC for filenames, releases, logs, and retention calculations. Never
   overwrite an existing recovery point.
9. Use an exclusive lock so a slow backup cannot overlap the next scheduled
   run or a manual run.
10. A failed backup must never stop, restart, recreate, or mutate the
    production application containers. It must retain the previous valid
    remote backups and exit non-zero.

### Backup Artifact Contract

Each run will produce:

- release/tag: `db-backup-YYYYMMDDTHHMMSSZ`;
- encrypted asset: `financee-db-YYYYMMDDTHHMMSSZ.dump.tar.enc`;
- checksum asset: the same name plus `.sha256`;
- a minimal non-sensitive release body containing UTC creation time,
  application Git SHA, database format version, success state, and retention
  class;
- inside the encrypted bundle:
  - `database.dump`, generated by `pg_dump --format=custom --compress=6
    --no-owner --no-acl`;
  - `manifest.txt`, containing the UTC timestamp, application Git SHA,
    PostgreSQL version, database name, schema count, and backup format version;
  - `SHA256SUMS`, covering the dump and manifest.

The dump must be taken from the PostgreSQL container through `docker compose
-f deploy/docker-compose.yml exec -T db`. `pg_dump` supplies a consistent
snapshot without stopping the site. The job must run `pg_isready` and
`python manage.py release_preflight` before dumping and must fail closed if
either check fails.

### Retention and Capacity Policy

- Keep the newest **30 daily** recovery points.
- Keep the first successful backup of each month for **12 months**.
- Delete only releases/assets that match the exact managed
  `db-backup-<UTC timestamp>` pattern; never delete unrelated releases.
- Delete the matching managed tag after deleting an expired release.
- Perform retention only after the current upload and remote verification
  succeed.
- Record encrypted size and warn at 1.5 GiB. Fail before upload at 1.9 GiB so
  the job never depends on the 2 GiB service boundary.
- If the encrypted database approaches the limit, stop this GitHub design and
  move to real object storage; do not split a database silently without first
  designing and rehearsing multipart restore.
- Keep at most one successfully verified bundle locally and remove it on the
  next successful run. Always remove plaintext temporary files through a
  restrictive `umask 077` temporary directory and cleanup trap.

### Monitoring and Failure Handling

- Systemd/journald must record start time, finish time, duration, encrypted
  size, release identifier, verification result, retention result, and a
  scrubbed failure category.
- Add a daily freshness check: newest verified remote backup must be no older
  than 26 hours. Two consecutive failures or age above 26 hours is an
  operations incident.
- Initial notification can use a GitHub Issue in the private backup repository
  or another owner-approved channel, but notification failure must not hide the
  backup failure. Deduplicate open failure issues and close the incident only
  after a later verified backup.
- Alert categories: preflight failure, dump failure, encryption failure,
  local-disk shortage, size-limit breach, authentication failure, upload
  failure, remote checksum/decryption failure, retention failure, and stale
  recovery point.
- Never delete the latest known-good release while investigating a failure.

### Rollback / Removal

Disabling this feature means disabling the systemd timer first, waiting for any
active locked job to finish, then removing the service/timer and EC2 GitHub
credential. It must not remove PostgreSQL data, Docker volumes, application
configuration, the existing Phase 28 scripts, or remote backups. Remote
releases may be deleted only through a separate owner-approved retention or
decommission action after a final restore rehearsal.

## [ ] MAJOR UPDATE: Add Quantity-Based Companies Without Disturbing Serial-Based Companies

### Objective

Financee currently supports serial-number-based inventory only. Every purchased
unit receives a serial number, and sales and returns operate on those individual
serialized units. This behavior is stable and must remain available without
functional or accounting regressions.

Add a second company type:

1. **Serial-based company** — provisions and uses the existing tenant schema and
   preserves all current behavior.
2. **Quantity-based company** — provisions a separate tenant schema designed
   around aggregate item quantities. Purchases, sales, purchase returns, and
   sale returns use manually entered quantities and never require serial
   numbers.

The admin company form must require the operator to choose the company type.
Once a company is provisioned, its type controls schema provisioning, backend
behavior, screens, validation, reports, and tests. Both types must use the same
visual theme and shared authentication, subscription, permissions, feature
flags, attachments, deployment, and administration infrastructure.

### Phase 0 Decision Worksheet

Reply with the question number and your selected answer. The recommended
defaults are designed for the safest first release and can be changed before
the Phase 0 gate is approved.

1. **Inventory costing method**
   - Recommended: **perpetual weighted-average cost**.
   - Alternative: FIFO cost layers.
   - Decision: **APPROVED — FIFO cost layers**.

2. **Quantity precision**
   - Approved units include Pieces, Boxes, Kilograms, Grams, Litres, and Metres.
   - Pieces and Boxes use whole-number quantities only.
   - Weight, volume, and length items support up to three decimal places.
   - Decision: **APPROVED — per-item unit rules with `numeric(18, 3)` quantity
     precision; Pieces and Boxes must have a zero fractional part**.

3. **Negative stock**
   - Never allow a sale, purchase return, edit, deletion, transfer, adjustment,
     or backdated transaction to make stock negative.
   - Show a clear warning with available and requested quantity, but the warning
     must not provide an override that permits negative stock.
   - Decision: **APPROVED — block negative stock with user warnings**.

4. **Warehouses and locations**
   - Quantity companies require multiple warehouses in the first release.
   - Purchases, sales, returns, opening stock, transfers, adjustments, counts,
     availability checks, and stock reports must be warehouse-aware.
   - Decision: **APPROVED — multi-warehouse in the first release**.

5. **Batch, lot, and expiry tracking**
   - Decision: **APPROVED — exclude batch, lot, and expiry tracking**.

6. **Item variants**
    - Quantity companies require item variants.
    - Required variant dimensions: brand, model, color, storage, RAM, region, and
      condition.
    - Every unique sellable variant combination receives a unique SKU.
    - The system suggests the SKU automatically; an authorized user may enter
      or edit it manually only before the item/variant has transactions.
    - Decision: **APPROVED — required dimensions and SKU identity/lifecycle
      confirmed**.

7. **Units of measure**
   - No unit conversion is required. Each item/variant has one inventory unit.
   - A product stocked as Pieces and a product stocked as Boxes must be separate
     item/SKU records unless a later conversion feature is approved.
   - Decision: **APPROVED — one unit per item/variant, no conversions**.

8. **Backdated transactions**
   - Backdated transactions are required.
   - They must be limited to open periods and must recompute affected FIFO
     layers, COGS, stock balances, and reports safely.
   - Any backdated operation that would create temporary/final negative stock or
     invalidate later consumption must be blocked with an explanation.
   - Decision: **APPROVED IN PRINCIPLE — backdating allowed with open-period,
     FIFO-reflow, and non-negative-stock guards**.

9. **Editing posted documents**
   - Posted invoices must be editable.
   - Edits must atomically rebuild affected FIFO layers, stock movements,
     journals, party balances, COGS, and reports.
   - An edit must be blocked when downstream transactions cannot be preserved
     safely; the UI must state why it is blocked.
   - Decision: **APPROVED IN PRINCIPLE — guarded posted-document editing**.

10. **Sale-return valuation**
    - Recommended: reverse the exact historical COGS assigned to the original
      sale line and restore that value to inventory.
    - Decision: **APPROVED — restore the exact original FIFO cost**.

11. **Purchase-return valuation**
    - Recommended: return at the original purchase-line unit cost and block the
      return if sufficient eligible stock from that purchase cannot be
      established under the selected costing model.
    - Decision: **APPROVED — original purchase cost with FIFO eligibility
      guard**.

12. **Cumulative return rules**
    - Recommended: allow multiple partial returns, but never allow total sale or
      purchase returns to exceed the original line quantity.
    - Decision: **APPROVED — partial returns allowed; cumulative quantity may
      never exceed the original line quantity**.

13. **Inventory adjustments and physical stock counts**
    - Physical stock counts are required in the first release.
    - The system must compare counted and system quantities per
      warehouse/item/variant and post an approved adjustment for differences.
    - Adjustments require a reason, permission, FIFO valuation rule, balanced
      journal, and immutable audit trail.
    - Decision: **APPROVED — physical counts and controlled adjustments**.

14. **Company-type immutability**
    - Recommended: company type is permanently immutable after provisioning.
      Any future serial-to-quantity conversion must be a separate migration
      project that creates and reconciles a new schema.
    - Decision: **APPROVED — company type is permanently locked after
      provisioning**.

15. **Document numbering**
    - Recommended: sequential document numbers per tenant and document type,

    - Alternative: retain only the current database IDs.
    - Decision: **APPROVED — separate sequences per document type, such as

16. **Taxes, discounts, and currency**

    - Both percentage and fixed-amount discounts are required.
    - Discounts must be supported at both line and whole-invoice level.
    - Discounts reduce taxable value before tax by default. Store the applied
